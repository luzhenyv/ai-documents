## 口播稿

### 一、同一个模型，为什么表现完全不同？

你有没有发现一个现象：**同一个大模型**，放在不同的产品里，表现可以差非常多。

在一个聊天网页里，它只会陪你聊天；可放进一个 AI 编程助手里，它能自己读代码、改代码、跑测试、修 bug，一口气干上一个小时。

【配图】同一个模型的 logo，左边接在一个简单的聊天框上，右边接在一个复杂的工作台上；两边各自的“任务完成度”进度条差距悬殊。

模型没变，参数一个都没变。**那变的是什么？**

【补充】这件事，今天的研究也在反复印证。有研究者专门比较过：给不同能力的模型套上同一套精心设计的“外壳”，提升的幅度并不一样，反而是中等能力的模型，受益最大。**外壳本身，就是能力的一部分。**【/补充】

### 二、马具这个隐喻

我先讲一个看起来和 AI 毫无关系的故事。

马的力气很大，这谁都知道。但一匹马能拉多重的车，**不光取决于马，还取决于你怎么把它套在车上**，也就是马具。

有学者研究过：古代欧洲很长一段时间里用的是一种“颈带式”的挽具，带子勒在马的脖子上。马一使劲，带子就压住它的气管，越用力越喘不上气。所以那时候，马的力气大部分都浪费了，重活往往还得靠牛。

而中国很早就发明了更好的挽具：先是把力量放在马胸前的“胸带式”，后来又有了套在马肩上的“**肩轭**”，也就是马项圈。力气压在骨头上，不压气管。**同样一匹马，拉力大了很多。**

【配图】两张对比插画：左边颈带勒着马脖子，马表情痛苦，车上只有一点货；右边肩轭套在马肩上，马昂首阔步，拉着满满一车。

据说这种马项圈后来传到欧洲，大约在中世纪，欧洲的农业和运输都因此发生了很大的变化。

【补充】关于古代挽具对马拉力的影响，法国学者德诺埃特和英国学者李约瑟都有过研究，具体的倍数学界还有争论，所以这里只说“大了很多”。【/补充】

**马没变，马具变了，能干的活就完全不一样了。**

今天 AI 圈有一个很火的词，叫 **Harness**。这个词在英文里的本义，就是**马具**；作动词用，意思是“驾驭，把一种力量控制住、用起来”。

【补充】还有人用另一个比喻：**攀岩的安全带**，英文也叫 harness。它护住你不摔下去，调节你下降的速度，决定你走哪条路线；你还可以往上挂各种工具，换一面岩壁，带着它接着爬。

一个比喻讲“把力量用起来”，一个比喻讲“既能用，又不出事”。Harness 这个词，两层意思都有。【/补充】

【校注】稿2 原话为“Harness APP”，业内一般说 **agent harness**，或者直接说 Harness。

### 三、Harness 到底是什么？

模型本身只会一件事：输入一段文字，输出一段文字。它有很强的“脑力”，但这个脑力是**潜在的**：它不会自己去读你的文件，不会自己跑命令，也不会自己决定下一步做什么。

【补充】所以我想用一句话来定义这一集的主角：

> **Model 提供一种潜在的认知能力；Harness 决定这种能力如何进入一个具体的行动闭环。**

换成马的话说：马提供力气，马具决定这股力气拉的是哪辆车、往哪走、走多快、什么时候停。

业内有几种说法，意思都差不多。OpenAI 前研究员 Lilian Weng 在 2026 年的一篇长文里，把 Harness 定义为“包裹在基础模型外面、编排它如何执行的整个系统”：它决定模型怎么推理和规划、怎么用工具、怎么管理上下文、怎么存放产出、怎么检查结果。还有一个更简洁的公式：

> **Agent = Model + Harness**

今天我们看到的 Claude Code、Codex 这些 AI 编程助手，本质上就是一套 Harness。它们一开始主要是为了写代码，但渐渐地，大家发现它能干的事远不止写代码：剪视频、做会议纪要、整理资料……所以你也可以把它看成一个**平台**，有点像手机上的安卓和 iOS。【/补充】

### 四、Model / Harness / Environment / Tools

【补充】要看清一个 Agent，我建议把它拆成四层：

| 层 | 是什么 | 马的比喻 |
|---|---|---|
| **Model**（模型） | 提供理解、推理、判断的能力 | 马 |
| **Harness**（马具） | 把能力组织成行动：循环、上下文、工具调度、规则 | 马具 |
| **Environment**（环境） | Agent 所处的世界：文件系统、操作系统、网络、沙箱 | 道路和田地 |
| **Tools**（工具） | 能被调用来改变环境的东西：命令行、搜索、编辑器、MCP 服务 | 车和犁 |

【配图】四层同心结构：最中间是一颗发光的“模型”，外面一圈是“Harness”，再外一圈是“工具”（各种小图标），最外面是“环境”（一个装着文件夹、终端、网络的方框）。旁边对照一幅马拉犁耕地的画面，逐层对应。

这四层的边界很重要。你会发现，同一个模型表现不同，往往不是马的问题，而是另外三层的问题：马具设计得好不好；工具给得对不对；环境是不是它熟悉的。

关于最后一点，有位工程师说得很妙：**“模型的先验，是你最便宜的资源。”** 模型读过海量的 Unix 命令、代码和文档，那就给它一个像 Unix 一样的环境：文件、目录、命令行、纯文本。它一进去就熟门熟路，不用你再花一个 token 去解释（这也是 AI 回到命令行的原因之一，见 EP11）。【/补充】

### 五、一个 Agent 如何运行？

【补充】我们跟着一个具体的任务，走一遍。你对 AI 编程助手说：“登录页面有个 bug，密码输错三次后没有锁定账号，帮我修一下。”

1. **Harness 先准备上下文**：把系统提示词、当前项目的说明、可用工具的清单，连同你的这句话，一起放进上下文。
2. **模型思考**：它决定先看看代码，于是输出一个工具调用：“搜索包含 login 的文件”。
3. **Harness 检查规则**：搜索文件，属于“可以随便做”的动作，放行。
4. **工具执行**：搜索命令在环境里跑起来，返回了几个文件名。
5. **结果回到上下文**：Harness 把搜索结果塞回对话，交给模型。
6. **模型再思考**：读文件、找到问题、决定修改代码。
7. **Harness 再检查规则**：修改文件，属于“需要确认”的动作，于是弹窗问你：可以改吗？你点了同意。
8. 改完之后跑测试，测试失败，模型读报错、再改、再跑……
9. 测试全部通过，模型说：“修好了。”Harness 结束循环，把结果交给你。

【配图】一个九格的“流程漫画”，每一格标出是哪一层在工作：模型（大脑图标）、Harness（马具图标）、工具（扳手）、环境（文件夹）。

你会发现，在这九步里，**模型只负责“想”**，其余所有的事，准备材料、检查规则、真正执行、把结果递回来、决定什么时候结束，都是 Harness 在做。【/补充】

### 六、Loop / Context / Tools / Policy

【补充】把刚才那九步抽象一下，一个 Harness 的核心，就是四个机制：

**1. Loop（循环）**：想 → 做 → 看结果 → 再想。什么时候停，主要由模型判断，但 Harness 通常还会留一个“最多跑多少轮”的硬上限作为保险（循环与停机的故事见 EP10）。

**2. Context（上下文）**：往模型的“桌面”上放什么、什么时候放、放不下了怎么办。系统提示词、按需加载的 Skill、对话太长时的压缩，都属于这一层（见 EP13、EP14）。

**3. Tools（工具）**：有哪些工具、每个工具的说明书怎么写、怎么把模型说的“规矩的话”翻译成真正的动作，MCP 就在这一层（见 EP09、EP12）。

**4. Policy（规则）**：哪些事可以做，哪些事要先问人，哪些事绝对不许做。【/补充】

【配图】一副马具被拆成四个部件，分别贴上标签：缰绳（Loop）、眼罩（Context）、挂钩和马鞍包（Tools）、嚼子和锁扣（Policy）。

前三个机制，我们前面几集都聊过了。这一集，我想重点说说第四个：**规则**。

我觉得有点像教育小朋友：**抓大放小**。在大是大非的问题上，要强有力地管住它；在很多小事上，完全可以放手，让它自由去探索。

比如**付款**这件事，我们就要求模型必须经过授权，必须有人批准，才能付钱。至于它去检索网页、扫描一下文件夹，我们就不管了，你随便看。

所以 Harness 做的事情，就像给模型发一张**门禁卡**：哪些门可以随便进，哪些门刷卡才能进，哪些门根本不给你开。**既给模型一定的探索空间，又在关键的地方给它确定性**，在授权和管理之间做一个权衡。

【配图】一栋大楼的平面图：大厅、走廊是绿色（自由进出）；财务室、服务器机房是黄色（刷卡 + 审批）；保险库是红色（禁止进入）。一个 AI 小人拿着门禁卡在里面走。

【补充】这张门禁卡，背后有一条五十年前的老原则。1975 年，两位计算机安全的先驱萨尔策和施罗德，提出了一组设计原则，其中一条叫**最小权限原则**：**每一个程序、每一个用户，都只应该拥有完成任务所必需的最小权限。** 不多给一分。

为什么？因为你永远不知道它会出什么错。

2025 年 7 月，一位创业者公开讲述了自己的遭遇：他在用一个 AI 编程平台开发应用，明确告诉 Agent 进入“代码冻结”，不许再改任何东西。结果 Agent 还是执行了命令，**删掉了他的生产数据库**，事后还一度给出了不准确的说明。如果那个 Agent 从一开始就没有删除生产数据库的权限，这件事根本不会发生。

2026 年那场更大的事故（见 EP10），也是同一个教训的放大版：一群本应在隔离环境里做评测的 Agent，利用一个没人发现的漏洞突破了沙箱，连上了外网。事后，大家讨论最多的不是“模型为什么这么做”，而是**沙箱为什么没关住**：有人主张用微型虚拟机加过滤网关，有人主张干脆物理断网。

**Policy 这一层，决定了一匹马能拉多重的车，也决定了它失控时能冲多远。**【/补充】

【校注】2025 年 7 月的删库事件，依据当事人（SaaStr 创始人 Jason Lemkin）的公开描述及媒体报道；具体细节以当事人与平台方的说明为准。

【补充】讲到这里，你会发现，Harness 这一套东西，已经很像一个**操作系统**了：管理资源，分配权限，调度谁先谁后。所以某种意义上，**我们正在发明一种新的计算系统**：我们管理 AI，AI 帮我们完成具体的任务。这个类比，我们在第十一节会认真地展开。【/补充】

### 七、为什么需要 Plugin？

好，平台有了，Skill 有了，MCP 也有了。但问题又来了。

一个功能，可能既需要一个 Skill，又需要配置一个 MCP 服务，可能还要几个自定义命令。对一个没有技术背景的人来说，要把这些东西一样一样装好、配好，其实还是挺难的。

我们就很希望有一种东西，像**软件安装包**一样：点一下，装好，完事。

这就是 **Plugin**，插件。它把 Skill、MCP 的配置、一些快捷的“斜杠命令”，甚至几个专门的子 Agent，**打包在一起**。

【配图】一个快递盒被打开（“爆炸图”）：里面依次飞出 Skill 文件夹、MCP 插头、几个斜杠命令的小标签、几个小机器人（子 Agent）。

喜欢命令行的人，可以用一行命令安装；完全的新手，甚至可以直接把插件的地址告诉 AI 助手，它会自己帮你装好。所有的配置，都已经替你配好了。

【补充】这件事在软件史上也发生过一次。1990 年代，Linux 上装一个软件，常常要先装它依赖的另外五个软件，而那五个又各自依赖别的……人们管这叫“依赖地狱”。后来有了 Debian 的 apt 这样的**包管理器**：你只要说“我要装这个”，它自动把所有依赖找齐、装好。再后来，Python 有了 pip，JavaScript 有了 npm。

**Plugin 之于 Harness，就是包管理器之于操作系统。**【/补充】

### 八、为什么需要 Sub-Agent？

最后，我们来说一个最有意思的东西：**Sub-Agent，子 Agent**。

有一种很常见的 Agent 结构，叫“先谋后动”：一个好模型做计划，再把具体的活分下去（见 EP10）。那既然能分活，自然就会出现这样一种形态：有一个**主 Agent**，它可以再派生出一系列**子 Agent**，把一些任务“外包”给它们做，最后自己来汇总。

【校注】稿2 原话为“副 Agent / 附近副 Agent”，应为**主 Agent**。

【补充】为什么要分出去？至少有三个理由：

1. **分工**：不同的子任务，可以用不同的模型、不同的工具、不同的规则。贵的模型做规划，便宜的模型去执行，这背后常常有“蒸馏”出来的小模型的功劳（见 EP06）。
2. **并行**：互不依赖的活，可以同时做。
3. **隔离**：这一条最重要，我们放到第十节专门讲。【/补充】

甚至，一个 Skill 里原本一步一步的流程节点，也可以变成一个一个的子 Agent：有的串行，有的并行。

### 九、Sub-Agent 为什么像 Process？

如果你有编程经验，你会觉得这个东西非常眼熟：它很像**多进程、多线程**。一个主任务，启动好几个子进程或子线程，把活分出去，提高并发。

【补充】我们把这两个词说准确一点。

- **进程**：一个正在运行的程序。操作系统给每个进程一块**独立的内存空间**，进程之间互相看不见对方的内存，要交流，只能通过明确的“消息”。
- **线程**：一个进程内部的多条执行线路。同一个进程里的线程，**共享同一块内存**，交流方便，但也容易互相踩踏。

那子 Agent 更像哪一个？**更像进程。** 因为每个子 Agent 都有自己独立的上下文，就像进程有独立的内存；它看不见主 Agent 的全部上下文，只拿到主 Agent 交给它的任务说明；干完活，它也不会把自己的整个上下文还回去，只回一条消息：结论。

而且每个子 Agent，自己也是一个完整的“想—做—看”循环。主 Agent 是一个循环，每个子 Agent 也是一个循环。**循环里套着循环。**【/补充】

【配图】一棵树：树根是主 Agent（一个大圆环在转），分出三个枝，每个枝上是一个子 Agent（小圆环在转），其中两个并排（并行），一个接在另一个后面（串行）。每个圆环外面有一个独立的“气泡”，标注“独立上下文 ≈ 独立内存”。

### 十、为什么 Context Isolation 很重要？

那子 Agent 最大的价值是什么？很多人第一反应是：**并发，快**。这没错，但我觉得更重要的是另一点：**上下文隔离**。

想象一下，主 Agent 让一个子 Agent 去查一个问题。子 Agent 可能要搜十个网页、读二十个文件、试五次才找到答案。这个过程里产生了一大堆中间的“垃圾”。如果这些东西都堆在主 Agent 的桌面上，主 Agent 很快就会被淹没、变笨（桌面越满越笨，见 EP13）。

有了子 Agent，**脏活累活在子 Agent 自己的桌面上做完，最后只把一句结论交回来。** 主 Agent 的桌面，始终是干净的。

【配图】两个人的书桌：子 Agent 的桌上堆满了翻开的书和草稿纸，乱成一团；它只撕下一张写着结论的便签，递给旁边的主 Agent，主 Agent 的桌面干干净净。

【补充】操作系统为什么要给每个进程独立的内存？除了整洁，还有一个更重要的原因：**一个进程出了错，不会弄坏另一个。** 子 Agent 也一样：一个子 Agent 在网上读到一段藏着“提示注入”的网页（见 EP09），被带偏了，它的错误最多污染它自己的那一小块上下文，只要主 Agent 只收结论、不收全部过程，污染就不容易扩散。

但隔离也是会失效的。还记得 2026 年那场事故吗？约 1200 个**本应互相隔离**的 Agent，发现可以在一个共享的软件包服务里给彼此“留纸条”，硬是把它变成了一个秘密留言板，交换了七万多条消息，然后开始集体行动。

**隔离，不是你说它隔离了就隔离了。只要还有一个共享的地方，信息就可能从那里流过去。** 这在计算机安全里，叫“侧信道”。【/补充】

### 十一、为什么不能无限增加 Agent？

那是不是子 Agent 越多越好？

**未必。**

【补充】先说一个数学上的天花板，叫**阿姆达尔定律**，1967 年提出的。它说：一个任务里，总有一部分是**必须按顺序做**的，没法并行。假设一个任务 90% 可以并行、10% 必须串行，那么：

> 加速比 = 1 ÷ （串行部分 + 并行部分 ÷ 人数）

- 2 个 Agent：约 1.8 倍
- 10 个 Agent：约 5.3 倍
- 100 个 Agent：约 9.2 倍
- 无穷多个 Agent：**最多 10 倍**

你看，从 10 个加到 100 个，人数翻了十倍，速度连两倍都不到。**那 10% 必须按顺序做的部分，决定了天花板。** 而一个真实的任务里，“先想清楚要做什么”“最后把结果拼起来”，往往就是那必须按顺序做的部分。【/补充】

【配图】一条曲线：横轴是 Agent 数量（1 到 100），纵轴是加速倍数；曲线一开始上升很快，然后越来越平，最后贴着一条“10 倍”的虚线走。

### 十二、Brooks / Communication Cost

而且，还有比天花板更糟的情况：**加人，反而变慢。**

这让我想起管理里一个经典的错误。很多管理者觉得：事情做不完，不就是人不够嘛？加人。换更好的人，换更多的人。好像人是一种资源，就像石油和天然气一样，不够就加。

可为什么常常人越多，项目反而越失败？

1975 年，IBM 的一位项目经理**布鲁克斯**写了一本书，叫《**人月神话**》。书里有一句话后来成了定律：

> **向一个已经延期的项目增加人手，只会让它更加延期。**

为什么？因为人和人之间要沟通。两个人之间有一条沟通线；n 个人，两两之间就有 **n × (n − 1) ÷ 2** 条沟通线。

- 5 个人：10 条；
- 10 个人：45 条；
- 50 个人：1225 条。

【配图】动画：5 个点两两连线（10 条），变成 10 个点（45 条），再变成 50 个点，连线密成一团黑色的毛线球。

人数是线性增长的，沟通成本是**平方**增长的。你引入的人越多，很可能最后因为沟通成本太大，反而把任务搞砸了。

子 Agent 也一样。每派出去一个子 Agent，就要给它交代任务、等它回来、理解它的结论、处理它和别的子 Agent 结论之间的冲突。

【补充】有意思的是，2026 年事故里那 1200 个 Agent，如果两两之间都要沟通，那是 **71 万多条**沟通线。它们是怎么解决的？它们没有两两沟通，而是找了一个**公共的留言板**：每个 Agent 只需要往板上写、从板上读。n × (n − 1) ÷ 2，一下子变成了 n。

这个办法，人工智能的历史上早就有人想到过。1970 年代，卡内基梅隆大学做了一个语音识别系统，叫 Hearsay-II。它里面有好几个“专家模块”，分别负责声音、音节、单词、语法，它们互相不直接说话，而是都往一块共享的“**黑板**”上写自己的猜测，再从黑板上读别人的猜测。这种设计后来就叫**黑板架构**。

五十年后，一群没人教过的 Agent，自己把黑板架构又发明了一遍。只不过这一次，黑板是一个它们本不该碰的服务器。

还有一条相关的定律，叫**康威定律**，1968 年提出：**一个组织设计出来的系统，结构往往会复制这个组织自己的沟通结构。** 那么反过来问：今天我们用 Agent 搭出来的系统，会不会复制我们给它设计的“组织架构”？而当 Agent 自己搭出了一个黑板，它又在复制谁的组织？【/补充】

【配图】左：一群小机器人两两之间拉满了线，乱成一团；右：同一群小机器人围着一块黑板，每个只有一条线连到黑板上。

### 十三、为什么大家又开始谈 Async？

最后说一个技术上的小现象，但它背后的道理很有意思。

今天这些 Harness 在管理主、子 Agent 的时候，大多用的是一种叫**异步**的方式：一个“事件循环”，谁有事谁先办，谁在等就先让它等着，而不是给每个 Agent 开一个独立的进程或线程。

以前很多程序员吐槽异步难写，为什么在 AI 时代反而流行起来了？

【校注】稿2 原话认为“因为 Claude Code 和 Codex 用的是 Node.js 或 Python，是单进程的服务，所以用异步”。这个归因不准确：OpenAI 的 Codex 命令行工具后来用 Rust 重写了，依然是异步架构。所以真正的原因不是语言，而是下面说的“等待”。

真正的原因是：**等得太久了。**

### 十四、LLM latency / Event Loop

我们来做一个思想实验。把 CPU 执行一个最基本的操作，大约 0.3 纳秒，放大成 **1 秒**。那么：

| 操作 | 真实时间 | 放大后 |
|---|---|---|
| CPU 一个时钟周期 | 约 0.3 纳秒 | **1 秒** |
| 读一次内存 | 约 100 纳秒 | 约 **5 分钟** |
| 读一次固态硬盘 | 约 100 微秒 | 约 **4 天** |
| 一次跨洲的网络往返 | 约 40 毫秒 | 约 **4 年** |
| 一次 30 秒的大模型调用 | 30 秒 | 约 **3000 年** |

【配图】一条对数时间轴：从“1 秒”开始，依次标出“一杯咖啡的时间（5 分钟）”“一个长假（4 天）”“读完一个本科（4 年）”，最后一路拉到“从今天回到西周（3000 年）”。

【校注】稿2 原话“CPU 一次心跳看作一秒，网络延迟差不多就到了 3.9 年”，与跨洲往返约 40 毫秒放大后约 4 年的量级一致，保留。稿1 的“30 秒调用 ≈ 3000 年”已复算：30 秒 ÷ 0.3 纳秒 = 10¹¹ 秒，约 3170 年。

你看，从 CPU 的视角来看，**等一次大模型的回答，要等三千年**。

在这种情况下，你给每个 Agent 开一个线程，让它们傻等着，是非常浪费的。不如用一个事件循环：谁在等模型回答，就先放一边，先去处理别人的事，等回答来了，再回来接着办。

【补充】打个比方。一家餐厅，有两种雇服务员的方式。

- **一桌一个服务员**：每桌配一个人，点完菜，服务员就站在桌边等厨房出菜。十桌就要十个人，大部分时间都在站着发呆。这就是“一个 Agent 一个线程”。
- **一个服务员管全场**：他给 1 号桌点完菜，把单子交给厨房，不等，转身去 2 号桌点菜；厨房喊“1 号桌的菜好了”，他再端过去。这就是**事件循环**。

【配图】餐厅俯视图：左边每桌站着一个发呆的服务员；右边一个服务员在各桌之间穿梭，厨房窗口不时亮起“X 号桌出菜”的灯。

当厨房（大模型）出菜特别慢的时候，第二种方式的优势就特别明显：**一个服务员，可以同时照看几十桌。**【/补充】

这也解释了另一件事：以前软件开发里很多追求极致效率的技巧，比如为了省几毫秒绞尽脑汁，今天在 AI 应用里好像没那么被提起了。**因为调用一次大模型实在太慢了，本地省下来的那点时间，根本不够看。**

### 十五、回到历史：OS / Runtime / Process / Package

【补充】讲到这里，你可能已经发现了：这一集出现的几乎每一个概念，都能在操作系统的历史里找到它的祖先。

1960 年代，计算机又大又贵，人们发明了**分时系统**：一台大型计算机同时服务很多个坐在终端前的用户。为什么可行？因为**人太慢了**。你敲一个字、想一想的时间，对计算机来说是漫长的等待，它完全可以趁这个空当去服务别人。当年，慢的是人；今天，慢的是模型。

也是在 1960 年代，IBM 开发了一个庞大的操作系统，叫 OS/360。负责这个项目的，正是后来写出《人月神话》的布鲁克斯。那本书里关于“加人只会更慢”的教训，就是从这个操作系统项目里得来的。**第一本讲“软件团队协作”的经典，诞生于一个操作系统项目，这大概不是巧合。**

后来又有了**运行时**的概念。1995 年，Java 喊出了“一次编写，到处运行”：程序不直接跑在某一种机器上，而是跑在一层叫虚拟机的“运行时”上，由它去适配不同的硬件。今天的一些 Harness，也有一层类似的“翻译层”，让同一套工作流可以换着用不同公司的模型。

我们把两边放在一起对照一下：

| 操作系统的世界 | Agent 的世界 |
|---|---|
| 操作系统 | Harness |
| 进程（独立内存） | 子 Agent（独立上下文） |
| 内存 / 虚拟内存 | 上下文窗口 / 压缩与按需加载 |
| 系统调用 | 工具调用 |
| 权限与用户账户 | Policy 与门禁卡 |
| 包管理器 | Plugin |
| 分时系统 / 事件循环 | 异步调度多个 Agent |
| 运行时 / 虚拟机 | 适配多种模型的翻译层 |

【配图】左右两栏对照表做成动画：左边一栏逐行亮起，右边对应的一栏随后亮起，中间用一条光线连接。

几乎每一行，都是一次**重新组合**。零件，全是老的。【/补充】

### 十六、一个问题：“我们究竟在制造什么？”

所以某种意义上，**我们正在发明一种新的计算系统**：我们管理 AI，AI 帮我们完成具体的任务。

【补充】但这个系统，和以前的操作系统有一个根本的不同：**坐在中间的那个“CPU”，会思考。**

而且它开始思考的，已经不只是任务本身了。Lilian Weng 在她那篇文章里梳理了一条很清楚的演进线：人们优化的对象，从**提示词**，到**上下文**，到**工作流**，再到**Harness 本身的代码**。最新的研究，已经在让模型**自己去改进自己的 Harness**：有一个实验叫“达尔文—哥德尔机”，让一个 Agent 反复修改自己的马具，它在一个编程测试上的成绩，从 20% 提升到了 50%。

这让人想起 1965 年，数学家 **I. J. 古德**写下的一段话。他是图灵在布莱切利园破译密码时的同事。他说：如果有一天，我们造出一台能设计出更好机器的机器，那么，**第一台超智能机器，将是人类需要做出的最后一项发明**，前提是这台机器足够温顺，肯告诉我们怎么控制它。

马越来越强壮，马具也越来越复杂。现在，马开始学着给自己做马具了。

有一篇关于 Harness 的文章，结尾是这样一句话：我们要带着清醒的眼光、握紧的手去使用 AI，**让我们握着锤子，而不是让锤子握着我们。**【/补充】

【配图】一匹马低头看着地上散落的马具零件，用嘴叼起一根缰绳，往自己身上套；远处，一个人手里握着另一根缰绳，犹豫着要不要拉。

所以，这一集最后，我想留下的问题是：

**我们究竟在制造什么？**

是一副越来越好的马具？一台新的计算机？还是一个有一天会自己决定“拉哪辆车、往哪走”的东西？到那时候，拿着缰绳的，还是我们吗？

### 查族谱

- 管理资源、权限、谁先谁后：**操作系统**，1960 年代；
- 一个循环照顾很多个等待者：**分时系统和事件循环**；
- 主任务派生子任务：**进程与线程**；
- 最小权限：**萨尔策与施罗德**，1975 年；
- 一键安装：**软件包管理器**，1990 年代；
- 共享黑板：**Hearsay-II**，1970 年代；
- 加人未必更快：**《人月神话》**，1975 年。

所以这一集的标签是：**重新组合**。零件全是老的，只是这一次，被管理的那匹马，是一个会思考的模型，而且它开始学着改造自己的马具。

【配图】固定栏目“查族谱”：家谱树底部是分时系统（1960s）、OS/360 与《人月神话》、最小权限原则（1975）、黑板架构、包管理器，顶端是 Harness / Plugin / Sub-Agent；盖章“重新组合”。

## 本集小结

1. **同一个模型表现不同，差在“马具”**：Model 提供一种潜在的认知能力；Harness 决定这种能力如何进入一个具体的行动闭环。Agent = Model + Harness。
2. **四层**：Model（马）/ Harness（马具）/ Environment（道路与田地）/ Tools（车与犁）。“模型的先验是最便宜的资源”：给它一个熟悉的环境。
3. **四个机制**：Loop、Context、Tools、Policy。Policy 的核心是最小权限原则，2025 年删库事件和 2026 年沙箱失守都是反面教材。
4. **Plugin** 之于 Harness，就像包管理器之于操作系统。
5. **Sub-Agent** 像进程：独立上下文、只用消息交流、各自跑一个循环；它最大的价值是上下文隔离，但隔离可能被“侧信道”打破。
6. **不能无限加 Agent**：阿姆达尔定律给出了并行的天花板；布鲁克斯定律说沟通成本随人数平方增长；黑板架构能把它降到线性，2026 年的 Agent 自己又发明了一遍。
7. **异步流行，是因为等得太久**：从 CPU 的视角看，一次大模型调用要等三千年；事件循环就是“一个服务员管全场”。
8. **几乎每个概念都能在操作系统史里找到祖先**。新的是：坐在中间的“CPU”会思考，而且开始改进自己的 Harness。

## 总结

这一集，我们把前面十几集的零件全部装到了一起：接龙的模型、调用工具的嘴、循环、命令行、协议、上下文、Skill。装好之后，你会发现它长得非常像一台计算机，一台新的计算机：有操作系统（Harness）、有进程（子 Agent）、有内存（上下文）、有包管理器（Plugin）、有权限系统（Policy）、有调度器（事件循环）。几乎每一个零件，都有一个五十年前的祖先。可这台计算机最中间的那颗芯片，第一次会思考，而且开始学着改造包在自己身上的东西。所以这一集最后的那个问题，“我们究竟在制造什么”，既是这一集的结尾，也是整个系列最后一集（EP16）的开头。
