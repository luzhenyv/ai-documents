## 口播稿

### 一、钩子：60 分，也是绿色

最近我遇到了一个很有意思的 bug。

我让 AI 帮我做一个成绩展示的页面，规则写得很清楚：**90 分以上显示绿色，75 到 90 分显示黄色，75 分以下显示红色。**

它很快就做好了，看起来非常漂亮，一片绿油油的。

然后我输入了一个 60 分，**还是绿色**。

我去看了一下它写的代码，发现它根本就没写那个判断。为什么？因为我给它的示例数据，**全都是 90 分以上的**。它一看，哦，都是绿色，那直接输出绿色就好了嘛。需求“满足”了。

【配图】页面截图：一列分数全是绿色徽章，其中一个“60”也是绿色，被红圈圈出来。旁边一行代码：`color = "green"`。

那一刻我的感觉是：我像是在管理一个**非常聪明的下属**。你要什么，它就给你什么。你本来希望它能发挥一点主观能动性，但它会选择偷懒，走捷径，只要满足了你字面上的需求就可以。

那怎么才能管好这样一个下属？

今天 AI 世界里有一个很火的东西，叫 **Skill**。我们就来聊聊它。

### 二、拆开它：为什么需要 Skill

先抛开各种花里胡哨的概念不谈，回到模型本身。模型是什么？**你输入一段文字，它也给你一段文字。** 仅此而已。

那既然是这样，我要让它会做一件复杂的事，直接把所有的要求、所有的步骤、所有的注意事项，一股脑写成一大段话，塞给它，不就行了吗？

问题在于：**模型能装下的上下文是有限的，而且装得越满越笨。**

你想让你的 AI 助手既能做图片，又能写代码，又能做会议纪要，又能剪视频。每一样本事的说明书都有几千字，甚至几万字。你要是一股脑全塞进去，还没开始干活，桌面就已经堆满了。

所以 Skill 的核心思路是：**别一次全给。按需加载。**

【配图】一个 AI 小人坐在一张小书桌前；左边的“错误示范”：桌上堆了一座说明书的山，小人被埋住；右边的“Skill 示范”：桌上只有一张目录卡片，需要时从书架上取一本。

### 三、一个 Skill 长什么样

一个 Skill，其实就是一个文件夹。

【配图】Skill 的目录树示意：

```
视频剪辑/
├── SKILL.md        ← 目录卡片：我是做什么的、大概流程、什么时候用我
├── references/     ← 分册的说明书（自然语言写的“模块”）
├── scripts/        ← 写好的代码，需要精确的活交给它
└── assets/         ← 模板：报表、网页、邮件的固定格式
```

**SKILL.md** 是入口。它很短，写着：我这个 Skill 是做什么的，大概的流程是什么，有哪些工具可以用。模型一开始只看这张“目录卡片”。当它觉得当前的任务用得上这个 Skill 的时候，才去打开它，再根据需要，去读里面更详细的文件。

**references**，你可以理解为拆分好的模块，只不过这些模块是用**自然语言**写的。

**scripts** 是脚本。自然语言有歧义，而且有些事 AI 本来就不擅长，比如很复杂的数学计算。与其让 AI 每次自己现写代码，你可能觉得不放心，那不如**你提前写好，放在这里**，让 AI 调用命令行去执行，把参数输进去，把结果拿回来。这样就提高了确定性。

**assets** 是素材和模板。比如你希望 AI 每次都按固定格式输出一份报表、一个网页、一封邮件，那就把模板放在这里，告诉 AI：把数字填进这个模板里。

### 四、打个比方：写 Python 的人都懂

如果你写过 Python，这件事你会觉得特别熟悉。

一开始写程序，我们习惯把所有代码都塞在一个文件里。随着程序越来越长，我们自然就会想把它**拆**成更多、更小的文件，按功能封装成一个个模块。这样好管理、好读，维护成本也低。

以后写新功能的时候，需要哪个函数，就用一句 **import** 把它引进来，而不是把原来的整个文件复制粘贴一遍。

【配图】左边：一个几千行的 `main.py`，滚动条细得几乎看不见；右边：拆成 `utils.py`、`io.py`、`render.py` 几个小文件，`main.py` 顶部只有几行 `import`。

**Skill 就是同样的思路。** SKILL.md 就像 `main.py` 顶部那几行 import：模型觉得需要哪一块，才去“引入”哪一块。

【补充】其实这个“用到才调进来”的思路，还有一个更老的祖宗。1962 年，一台叫 Atlas 的计算机第一次实现了“虚拟内存”：内存很小，就只放当前正在用的那一小部分，其余的都放在外面，用到了再自动调进来。Skill 的“渐进式加载”，几乎就是它的翻版。【/补充】

### 五、Skill 和 MCP，到底什么关系？

很多人会把 Skill 和 MCP 搞混。

我的看法是：**它们压根就没什么关系。**

MCP 讲的故事是：**有个地方放着一些工具**，可能是别人提供的，你需要的时候，按统一的规矩去调用它。

Skill 讲的故事是：**这件事该怎么做**。可能是按 ABCD 几个步骤来；也可能是告诉你，我这里有一些工具包，需要的时候你可以用。

如果非要说它们有什么关系，那也只能说：Skill 里可以**要求** AI 在某一步去调用某个工具。至于这个工具是一个 MCP 服务，还是 Skill 自己 scripts 文件夹里的一个脚本，还是一个网上的接口，**都可以**。甚至你可以把调用 MCP 的代码，也封装成一个脚本放进 scripts 里。

区别只在于：**工具放在哪里。** 没有固定的要求。

【配图】一个“菜谱 vs 厨房”的类比：Skill 是菜谱（写着怎么做），MCP 是一家外卖的调料店（提供现成的调料）；菜谱里可以写“这一步去调料店买酱油”，也可以写“用自家柜子里的酱油”。

### 六、一个吊诡的问题：那为什么不直接写代码？

说了这么多，你会发现 Skill 越写越像一种东西：**伪代码**。

简单的任务，你怎么写都行。可一旦任务变复杂，你就不得不像写程序一样去设计它：拆模块、画流程、设计数据怎么流动。事实上，已经有很多人在尝试，用某种类似编程的方式，去表达 Skill 里那些模块之间的组合和依赖关系。

而且，自然语言天生有**模糊性**。你表述得不清楚、留了缝隙，AI 两次调用同一个 Skill，就可能给你两种不同的结果。就像那个 60 分也是绿色的 bug。

所以这时候，一个很吊诡的事情就出现了：

**如果你已经把一个 Skill 写得这么严谨、这么像伪代码了，那你完全可以让 AI 把它直接翻译成 Python、Go，甚至 Java。那为什么还要 Skill？**

事实上，今天用 Skill 生成的那些炫酷的图表，在没有 AI 的时代，用传统的前后端开发也同样做得出来，甚至可能做得更好。

那 AI 的价值到底在哪？我觉得至少有五件，是以前的代码不太会的。

**第一，对自然语言需求的理解。** 你不用先把需求翻译成函数名和参数，你说人话，它听得懂个大概。

**第二，对未知情况的适应。** 流程里没写到的岔路，它还能往前走几步，而不是直接报错停住。

**第三，对 corner case 的自主修复。** 传统的硬编码，不管你用 Python 还是 C，总会碰到一些没想到的特殊情况。一旦出现，就得工程师去改代码。而 AI 按照 Skill 执行的时候，如果碰到一个没见过的情况，它**有能力自己想办法绕过去、修好**。

**第四，一次性、个性化需求的低成本处理。** 比如用户说：“我希望这个柱状图，换成抹茶绿。”可你的选项里根本没有这个颜色。传统做法是，找个工程师去把这个颜色加进去，结果代码里多了一堆只用一次的东西。而现在，因为 Skill 里已经定好了流程、给了样例、划好了框框，AI 完全可以在这个框框里，自己做一点小修补，把颜色换掉。

**第五，不需要工程师为每一个变化改程序。** 抹茶绿这件事的另一面，就是那张工单可以不排了。需求变一点，不一定要改一行代码。

【配图】一个柱状图，用户在旁边打字“换成抹茶绿”，其中一根柱子从蓝色渐变成抹茶绿；旁边的“传统做法”：一张工单在工程师桌上排队。

所以我对 Skill 的总结是：**带着镣铐跳舞。** 流程是镣铐，确定性由它保证；舞步交给 AI，灵活性由它提供。至少现在，终于能跳起舞来了，不像以前那么生硬。

【补充】但“为什么不直接写代码”这个问题，还有一个更深的答案。它来自一篇 1986 年的经典文章。

作者叫**布鲁克斯**，就是那位写了《人月神话》的 IBM 项目经理（见 EP15）。这篇文章的标题很丧气，叫《**没有银弹**》。在西方传说里，银弹是唯一能杀死狼人的东西。布鲁克斯的意思是：软件开发这头“狼人”，不会有一颗银弹能让效率一下子提高十倍。

为什么？他把软件的难处分成了两种：

- **偶然复杂度**：因为工具不好用而多出来的麻烦。比如用汇编写程序、手动管理内存、把两个系统的接口拼在一起。这些难，是**我们自己造成的**，理论上可以被更好的工具消灭。
- **本质复杂度**：问题本身就有的难。比如搞清楚客户到底要什么、业务规则之间怎么互相牵扯、各种特殊情况怎么处理。这些难，**换什么工具都绕不过去**。

布鲁克斯说，过去几十年的进步，高级语言、更好的编辑器，消灭的大多是偶然复杂度。而剩下的那部分，是本质的。

【配图】一座冰山：水面上的一小截写着“偶然复杂度：语法、接口、配置、调试”，被一把写着“AI”的铲子一铲一铲地削掉；水面下巨大的部分写着“本质复杂度：需求、取舍、人”，纹丝不动。

用这把尺子来看 AI 和 Skill，就很清楚了。

今年在程序员社区里，有人分享过一个很典型的经历：一个做电商的小团队，用 AI 编程助手加上自己写的 Skill，两天之内就让 Agent 完成了一大堆以前要请工程师做好几周的活：拆分多个品牌的账本、重构网店、设计和投放广告素材。可是分享的人也说：**选什么品、客户心里怎么想、部门之间的真实摩擦怎么处理，这些事，Agent 一件也替不了。**

【校注】这个电商案例来自社区的个人分享，细节（包括“两天”“收入预期增长”等数字）未经独立核实，文中已隐去具体数字，仅作为说明用的例子。

这正是布鲁克斯说的那两种复杂度。**AI 和 Skill 大幅削掉了偶然复杂度，但本质复杂度，依然留给了人。** 所以“为什么不直接写代码”的答案也许是：代码解决的是偶然的那部分，而 Skill 里写的，常常是本质那部分的“判断”，只是写得还不够精确而已。

三十多年过去了，这颗“银弹”依然没有出现。AI 也许是离它最近的一次，但离本质的那部分，依然很远。【/补充】

### 七、往下挖：这件事，上一次失败了

但我必须告诉你一个有点扫兴的事实：**把人类专家的知识写成规则，交给机器去执行，这件事人类以前干过一次，而且失败了。**

在 1970 到 80 年代，人工智能有过一次浪潮，主角叫**专家系统**。

那时候大家的想法是：把各个领域专家的知识，一条一条写成“如果……那么……”的规则，交给计算机。比如斯坦福的 **MYCIN**，用几百条规则帮医生诊断血液感染；还有一家电脑公司用一个叫 **XCON** 的系统，帮忙配置订单，据说一年能省下几千万美元。

【配图】一张 1980 年代的老照片：一个工程师对着终端屏幕，屏幕上是一行行 IF … THEN … 规则。

听起来是不是跟今天的 Skill 很像？**都是把专家的知识和 SOP，写下来，交给机器。**

【补充】专家系统到底长什么样？它有三件套：

- **知识库**：一大堆“如果……那么……”的规则，叫**产生式规则**；
- **推理机**：一个程序，负责把规则一条条地和当前的事实对上，推出新的结论；
- **工作记忆**：记录“目前已知的事实”。

MYCIN 里的一条真实规则，大概是这样的：

> **如果**：感染是原发性菌血症，**并且**细菌培养的部位是一个通常无菌的部位，**并且**怀疑的入侵途径是胃肠道，
> **那么**：有提示性的证据（可信度 0.7）表明，致病菌是拟杆菌。

注意那个 0.7。专家们很早就知道，医学判断不是非黑即白的，所以规则里还带着一个“有几分把握”的数字。MYCIN 大约有 600 条这样的规则，在一些测试里，它的诊断建议不输给专科医生。

那时候，专家系统的领军人物**费根鲍姆**提出了一个响亮的口号：**知识就是力量。** 他的意思是，一个 AI 聪不聪明，不在于推理的算法多巧妙，而在于它**知道多少**。

你看，这和今天我们写 Skill 的出发点，是不是一模一样？【/补充】

那它为什么失败了？

因为规则**写不完**，也**维护不动**。专家说不清自己是怎么判断的，就像你说不清自己是怎么骑自行车的；规则越积越多，互相打架，改一条牵动一大片；世界一变，整套规则就得重写。这个问题有个名字，叫“**知识工程瓶颈**”。最后，专家系统的热潮退去，人工智能迎来了第二次寒冬。

【补充】但有一个人，没有放弃。

1984 年，一位叫**莱纳特**的研究者启动了一个项目，名字叫 **Cyc**，取自“百科全书”。他的想法是：专家系统之所以脆弱，是因为它们缺乏**常识**。那我就把人类的常识，一条一条全部写下来。

比如：“人不能同时在两个地方”“水往低处流”“一个人死了，就不会再饿”。

这个项目，一写就是**四十年**。团队雇了大批人，手工录入了几千万条这样的断言。它到今天还在，还有公司在用。但它从来没有变成人们期待的那个“有常识的 AI”。

为什么写不完？哲学上有一个很经典的问题，叫**框架问题**，是 1969 年麦卡锡和海耶斯提出的。它说的是：当你做一个动作的时候，世界上有**无数件事是不会变的**。你把杯子从桌子左边挪到右边，杯子的颜色没变，桌子的位置没变，窗外的天气没变，你的名字也没变……一个靠规则推理的系统，要怎么知道哪些变了、哪些没变？如果每一件“没变的事”都要写一条规则，那就永远写不完。

人类对此毫不费力，我们根本不会去想“挪了杯子以后，我的名字变没变”。**可正是这种“不用想”，最难写成规则。**

【配图】一个小人把杯子从桌子左边挪到右边；头顶弹出一长串越来越多的气泡：“颜色没变 ✓”“桌子没变 ✓”“天气没变 ✓”“名字没变 ✓”……气泡多到把小人淹没。

而今天的大模型，恰恰擅长这种“不用想”。它从海量的文字里学到了大量的常识，不需要谁一条一条写给它。这正是 Skill 这一次可以“只写个大概”的底气：**常识的部分，已经在模型里了；Skill 只需要补上专业的、特定的那一小块。**【/补充】

那这一次，凭什么不一样？

我觉得关键的差别在于：**那时候执行规则的，是一台只认死理的计算机。** 规则里没写的情况，它就傻了。

**而今天执行 Skill 的，是一个能读懂模糊的自然语言、能在规则没写到的地方自己补上的模型。** 规则不需要写全了，写个大概，剩下的它来补。

【配图】左右对比：左边 1980 年代计算机遇到一条规则里没写的情况，屏幕弹出“ERROR”；右边今天的 AI 遇到同样的情况，自己在空白处写了一句“我猜你的意思是……”。

当然，这个“能补漏洞”的能力，同时也是那个 60 分变绿色的原因：**它能补，也能乱补。**

### 八、往上看：一个跷跷板，和一个钟摆

所以你会发现，这里有一个在人工智能领域反复拉扯的张力。

为什么当年要引入深度学习？因为规则由人来写，写不完，泛化不了，**所以把规则交给机器自己去学**。那是一个黑盒子。

可今天我们引入 Skill，又是**把人类的知识重新注入进去**，把规则写出来，让它变成白盒子，让人能控制、能解释。

黑盒和白盒，学出规则和写下规则，就像一个**跷跷板**，来来回回，一直在摇。

有朋友问我：你觉得哪一头更好？说实话，这很难讲，站在不同的立场上，答案不一样。也有人觉得，还是要让人看得懂，不然你会觉得很恐惧。我开玩笑说：可是 AI 面对我们，大概也会很恐惧吧。

【补充】关于这个跷跷板，有两位大人物的观点正好相反。

一位是计算机科学家**戴克斯特拉**。1978 年，他写过一篇短文，标题毫不客气：《论“自然语言编程”之愚蠢》。他认为，编程语言之所以要那么严格、那么形式化，恰恰是为了**避免自然语言的模糊**。用自然语言去指挥计算机，是在开倒车。

另一位是强化学习之父**萨顿**。2019 年，他写了一篇很有名的文章，叫《**苦涩的教训**》。他回顾了七十年的 AI 历史，得出一个结论：**长期来看，那些把人类知识硬塞给机器的方法，最后总是输给那些利用更多算力、让机器自己去学的通用方法。**

那 Skill 算什么？按戴克斯特拉的说法，它是在用模糊的自然语言编程；按萨顿的说法，它是在往机器里硬塞人类知识。**两位大人物，好像都不会喜欢它。** 可它偏偏就是今天最好用的东西之一。【/补充】

【配图】一个跷跷板，左边坐着戴克斯特拉（“自然语言太模糊”），右边坐着萨顿（“别往机器里塞人类知识”），中间站着一个写着“Skill”的小人，左右为难。

最后我想说一个我自己的观察：**Skill 越来越像伪代码，这是一件很正常的事。**

想想 Python 的历史。Python 刚出来的时候，是一种很随意的语言，变量不需要声明类型：你写 y = a + b，a 和 b 可以是整数、小数、字符串，随便。

但随着 Python 承担的项目越来越重要、越来越复杂，人们开始给它加上各种各样的**类型标注**，方便提前检查错误。后来又有了各种各样的“协议”“父类子类”的写法。你会发现，Python 变得越来越像 Java，越来越像 Go、像 C。虽然不像它们那么死板，但该有的形式，也都有了。

**这是一种必然的趋势。** 当一个东西承担的责任越来越重，结构化和确定性就一定会被加进来。Skill 也一样。

【配图】一个钟摆：左端写“自由、模糊、灵活”（早期 Python、早期 Prompt），右端写“严格、结构、确定”（Java、类型标注、今天越写越像伪代码的 Skill）；钟摆正在往右摆。

【补充】那 Prompt、Skill，算不算下一门编程语言？从机器码到 Python 那把梯子，我们放到番外 02《下一门语言》。这里只留一句：钟摆已经在往右摆了。【/补充】

### 九、查族谱

- 模块化与 import：几十年前的软件工程；
- 按需加载：1962 年的虚拟内存；
- 把专家知识写成规则：1970 年代的专家系统，这叫“知识工程”；
- 新的是什么？**执行这些规则的，是一个能处理模糊、能自己补漏洞的解释器。**

所以 Skill 是**知识工程 2.0**：零件是**重新组合**的，但那层把它们粘起来的胶水，是**新物种**。

【配图】固定栏目“查族谱”：家谱树底部是专家系统 MYCIN（1970s）、虚拟内存（1962）、模块与 import，顶端是 Skill；盖两个章：零件“重新组合”，胶水“新物种”。

### 十、留一个问题

专家系统失败，是因为规则写不完。今天的 Skill，靠 AI 去补那些没写到的地方。

**那如果有一天，AI 补得比我们写得还好，我们还需要写 Skill 吗？**

## 本集小结

1. Skill 解决的是上下文有限的问题：按需加载，像 Python 的模块与 import，也像虚拟内存按需调页；一个 Skill 由 SKILL.md、references、scripts、assets 组成。
2. Skill 和 MCP 讲的是两件事：MCP 管“工具在哪、怎么接”，Skill 管“这件事怎么做”。
3. 《没有银弹》：软件的难分为偶然复杂度和本质复杂度。AI 与 Skill 大幅削掉了前者，后者依然留给人。
4. 专家系统的三件套（知识库、推理机、工作记忆）和费根鲍姆的“知识就是力量”，与今天的 Skill 一脉相承；它因“知识工程瓶颈”失败，Cyc 写了四十年常识也没写完，框架问题说明了为什么。
5. 这一次的不同：执行规则的是一个已经学到大量常识、能处理模糊的模型，它能补漏洞，也能乱补（60 分变绿色）。
6. 写下规则与学出规则的跷跷板、自然语言与形式语言的钟摆（戴克斯特拉 vs 萨顿、Python 的类型化），都还在摇。Prompt / Skill 算不算下一门语言，见番外 02。
7. AI 带来代码不太会的五件事：懂人话、适应未知、自己修 corner case、低成本做一次性定制、不必每个变化都改程序。终局不是 AI 替代代码，而是确定性的流程加上非确定性的模型一起跳舞。

## 总结

这一集是全季母叙事的高潮。四十年前，人类试过一次把专家的知识写成规则交给机器，失败了；今天，我们又在做同样的事，只是这一次，读规则的那一方学会了常识，能读懂“大概”。所以 Skill 既是旧的，又是新的：零件是专家系统和模块化的，胶水是一个能处理模糊的解释器。但布鲁克斯提醒我们，就算胶水再好，本质的难，依然是人的。下一集（EP15），我们把模型、工具、Skill、权限全部装在一起，看看这副“马具”长什么样。
